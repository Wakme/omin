## Problem Statement

AI 模型越来越强，但 "能不能 reach 到 AI" 成了瓶颈。用户只能坐在电脑前通过终端和 Claude Code 交互。出门后，AI 就不在了。需要一个工具让用户随时随地和 AI 沟通，不只是在电脑前。

## What Makes This Cool

**远程自由感。** 走在路上，手机发一条消息，CC 在 Mac Mini 上干活，结果飞书回传。这个 "AI 随时在线" 的体验是核心 delight。CC 还能主动找你：任务完成通知你，遇到问题问你确认。

**插件架构让这变成平台。** 工作用大象 IM，个人用飞书，都是插件。加一个新 IM 不改核心代码。CC 也是一个插件，遵循同样的插件协议。所有人、所有工具都是平等的客户端。

**状态管理是核心差异化。** Omni 不只是消息路由器，它管理对话的逻辑状态：AI 是否在执行、是否等你确认、上下文游标（rewind）。这些状态驱动用户体验——你在手机上能感知 AI 在干什么，能在飞书里点击确认，能回退到任意对话节点。这是纯消息协议做不到的。

## Constraints

- 个人使用，MVP 单用户
- 全部运行在 Mac Mini（常驻），无云端服务器
- 技术栈：TypeScript（Omni Core + 插件）+ Swift（灵动岛 P1）
- 数据存储：SQLite
- 至少需要两个 IM 插件：飞书（个人）+ 大象（工作）

## Premises

1. "我需要随时和 AI 沟通，不只是坐在电脑前" — 这是核心需求
2. Omni Core 自建，同时管理消息和状态
3. 状态管理是核心功能，不是附属：执行状态、确认流程、上下文游标
4. 插件架构有真实需求（飞书 + 大象两个 IM），不是过度设计
5. 灵动岛是 P1，不阻塞 MVP
6. MVP: Omni Core + 插件协议 + 飞书插件 + CC 插件 + CLI

## Approaches Considered

### Approach A: 最小可用
硬编码飞书集成，无插件系统。最快能用，但加大象要改核心代码。

### Approach B: 插件架构全做
插件协议 + 飞书 + 大象同时做。工作量大。

### Approach C: 协议先行 + 飞书 MVP（CHOSEN）
设计插件协议，MVP 只实现飞书插件。大象作为第一个新插件验证架构合理性。

### Approach D: Matrix 协议（已否决）
评估过 Matrix/Tuwunel 作为消息核心。结论：Matrix 只管消息传输，不管对话状态（执行状态、确认流程、上下文游标）。Omni 仍需自建状态管理层。两个外部依赖（Matrix + State Service）的复杂度高于单个自建 Omni Core。放弃。

## Recommended Approach

C. 设计一个干净的插件协议，MVP 只做飞书。理由：
- 插件架构有真实需求（大象 IM），不是过度设计
- 飞书 MVP 可以快速验证核心闭环
- 大象插件作为 "第二个插件" 天然验证协议设计
- 状态管理由 Omni Core 统一提供，插件不需要管

## Core Concepts

### Peer

Omni 中的参与实体，可以是人类或 AI。Peer 是消息的发送者和接收者，Plugin 是 Peer 使用的通信通道。一个人类用户在不同 IM 上注册为不同的 Peer（你在飞书和大象是两个人）。

```
Peer {
  id: string              // UUID, auto-generated
  name: string            // 显示名
  type: "human" | "ai"
  pluginName: string      // 使用的插件: "feishu" / "daxiang" / "claude-code"
  externalId: string      // 插件侧的用户 ID: 飞书 openId / 大象 userId / AI 引擎标识
  createdAt: timestamp
}
```

- 你（人类）通过飞书插件注册为一个 Peer，`externalId` 是飞书 openId
- 你（人类）也可以通过大象插件注册为另一个 Peer，`externalId` 是大象 userId
- Claude Code 通过 CC 插件注册为一个 Peer，`externalId` 是引擎标识
- 未来 GPT、Gemini 等都可以注册为 Peer

### 消息路由

消息路由两级过滤：

1. **Conversation 过滤**：消息只发给同一个 Conversation 内的参与者
2. **Peer 定向**：在同一 Conversation 内，消息附带 from Peer，Omni Core 据此决定发送目标

本质就是：同群内广播，但要知道谁是谁。

### Conversation State（对话状态）

每个 Conversation 有独立的状态机，由 Omni Core 管理。状态驱动消息处理和用户感知。

```
ConversationState {
  execution: "idle" | "executing" | "waiting_confirmation" | "done"
  contextCursor: messageId?            // 上下文游标
  pendingConfirmation?: {
    messageId: string
    options: string[]
    expiresAt?: timestamp
  }
}
```

**状态流转：**
```
idle → executing → done
                → waiting_confirmation → executing → done
                                           → idle（拒绝/超时）
                → idle（超时/中断/报错）
```

**状态与插件交互：**
- Omni Core 状态变化时通知所有相关插件
- IM 插件根据状态展示 UI（"正在执行..."、确认卡片、完成通知）
- AI 插件根据状态决定是否处理新消息（executing 时排队）

## Plugin Interface（插件协议）

```
interface OmniPlugin {
  name: string                          // "feishu" / "daxiang" / "claude-code"
  capabilities: "send" | "receive" | "both"

  // 生命周期
  async init(core: OmniCore): void      // 注册到 Omni Core
  async destroy(): void                 // 卸载

  // 消息
  async sendMessage(msg: Message): void  // 发消息到 Omni Core
  onMessage?(msg: Message): void        // 收到 Omni Core 转发的消息（回调）

  // 状态通知
  onStateChange?(conversationId: string, state: ConversationState): void
}

interface OmniCore {
  // Peer 管理
  registerPeer(person: Peer): void
  unregisterPeer(id: string): void
  getPeer(id: string): Peer

  // 插件管理
  registerPlugin(plugin: OmniPlugin): void
  unregisterPlugin(name: string): void

  // 消息路由（基于 Peer）
  publish(msg: Message): void           // Peer 发消息，Core 路由到同群其他 Peer

  // 对话管理
  createConversation(config: ConversationConfig): Conversation
  getConversation(id: string): Conversation
  listConversations(): Conversation[]

  // 状态管理
  getConversationState(id: string): ConversationState
  updateConversationState(id: string, update: Partial<ConversationState>): void
  // rewind 委托给 AI 插件（如 CC 插件的 SDK resumeSessionAt），Core 只更新 contextCursor
  rewindConversation(id: string, toMessageId: string): Promise<void>
}
```

### 两类插件

Omni 有两类插件，遵循同一个核心协议，但职责不同：

**IM 插件：** 负责人类用户的 IM 交互（飞书、大象等）。需要扩展能力：建群、文件、图片、富文本、确认卡片、状态展示。

**AI 插件：** 负责与 AI 后端通信。接收用户消息，通过 AI 引擎执行，将结果（流式事件）回传 Omni Core。

```
// IM 插件扩展接口（飞书、大象等实现）
interface IMPlugin extends OmniPlugin {
  // 群管理
  async createGroup(name: string, members?: Peer[]): Promise<Group>
  async listGroups(): Promise<Group[]>

  // 媒体消息
  async sendFile(conversationId: string, file: File): Promise<void>
  async sendImage(conversationId: string, image: Image): Promise<void>

  // 富文本
  async sendRichText(conversationId: string, content: RichContent): Promise<void>

  // 确认交互
  async sendConfirmation(conversationId: string, message: string, options: string[]): Promise<string>  // 返回用户选择

  // 状态展示
  async updateStatus(conversationId: string, status: ConversationState): Promise<void>
}

// AI 插件扩展接口
interface AIPlugin extends OmniPlugin {
  // 发消息给 AI，通过回调流式返回结果
  async chat(message: string, conversationId: string): Promise<void>

  // 中断当前执行
  async abort(conversationId: string): Promise<void>
}
```

**AI 插件设计说明：**
- `chat()` 不直接返回字符串，而是通过 Omni Core 的 `publish()` 流式推送事件（文本块、工具调用、结果等）
- 这样 IM 插件可以实时展示 AI 的执行进度，而不是等全部完成才返回
- `abort()` 从可选改为必选：基于 SDK 的 CC 插件天然支持中断，其他 AI 插件也应提供

### AI 插件实现

每个 AI 工具实现 AIPlugin 接口。MVP 只做 CC 插件：

| 插件 | 实现方式 | MVP |
|------|---------|-----|
| CC 插件 | `@anthropic-ai/claude-agent-sdk` `query()` | Yes |
| ADK 插件 | Agent Development Kit API | No (Phase 2) |
| Codex 插件 | `codex` CLI | No (Phase 2) |
| Custom Agent 插件 | 自定义 HTTP API | No (Phase 2) |

**CC 插件实现：** 使用 Claude Agent SDK（`@anthropic-ai/claude-agent-sdk`），通过 `query()` API 以进程内方式调用 CC 引擎。SDK 返回 `AsyncGenerator<SDKMessage>`，流式输出所有事件。

**为什么用 SDK 而不是 `claude -p`：**
- SDK 内置 session 持久化，自动管理上下文，Omni 不需要自己拼消息历史
- SDK 直接接收 Hook 事件（`hooks` 参数），不需要修改 `~/.claude/settings.json`
- SDK 内置 `canUseTool` 权限回调，可以直接接飞书确认卡片
- SDK 创建的 session 与 CLI 互通：CLI 可以 `--resume <sessionId>` 无缝接手
- SDK 内置中断机制（`query.close()` / `abortController`），不需要手动管理子进程

**CC 插件 session 管理：** 每个 Omni Conversation 通过 `conversation_participants` 表绑定一个 CC session。
- 首次对话：`query({ prompt, options: { persistSession: true } })`，从 `system/init` 事件获取 `session_id`，写入 `conversation_participants` 表（peerId = CC peer 的 UUID，sessionId = CC session ID）
- 后续对话：从 `conversation_participants` 表查出 CC peer 的 `sessionId`，`query({ prompt, options: { resume: sessionId } })`，SDK 自动加载历史上下文
- CLI 互通：用户在终端执行 `claude --resume <sessionId>` 即可接手同一对话
- Session 持久化由 SDK 处理，存储在 `~/.claude/projects/<slug>/<sessionId>.jsonl`

**CC 插件事件流处理：** `query()` 返回的 `AsyncGenerator<SDKMessage>` 包含所有事件类型：

```
system/init         → 获取 session_id
assistant           → AI 回复文本（流式）
result              → 最终结果（成功/失败/超预算）
tool_use            → 工具调用通知（用于状态展示）
tool_result         → 工具执行结果
error               → 错误信息
```

CC 插件将这些事件转换为 Omni 消息，通过 Omni Core 路由到 IM 插件。

**CC 插件权限与确认：** 通过 SDK 的 `canUseTool` 回调实现：
- CC 执行工具前，SDK 调用 `canUseTool(toolName, input)`
- CC 插件将请求转发给 Omni Core → IM 插件 → 飞书确认卡片
- 用户在飞书中点击"允许"或"拒绝"，回调传回 CC 插件
- CC 插件返回 `'allow'` / `'deny'` / `'takeover'`（takeover 转给 CLI）

**CC 插件中断策略：**
- 用户在飞书发 `/stop`：调用 `query.close()` 终止当前执行
- 使用 `abortController`：`new AbortController()`，传入 options，调用 `.abort()`
- `query.close()` 会清理底层进程和所有资源（MCP、pending requests）
- 中断后状态更新为 idle，通知用户

**CC 插件执行队列：**
- executing 状态下同一 Conversation 的新消息排队
- 当前 query 结束后（`result` 事件），自动处理下一条排队的消息
- 使用 `resume` 参数保证上下文连续

## Data Model

```
Peer {
  id: string              // UUID
  name: string            // 显示名
  type: "human" | "ai"
  pluginName: string      // 使用的插件: "feishu" / "daxiang" / "claude-code"
  externalId: string      // 插件侧的用户 ID: 飞书 openId / 大象 userId / AI 引擎标识
  createdAt: timestamp
}

Conversation {
  id: string              // UUID
  name: string            // "auth-review"
  createdAt: timestamp
  status: "active" | "stopped"
  context?: {
    workingDirectory?: string
  }
}

ConversationParticipant {
  conversationId: string   // UUID → Conversation.id
  peerId: string           // UUID → Peer.id（通过 Peer.pluginName 知道用哪个插件）
  sessionId: string        // 插件侧会话 ID: 飞书 groupId / CC sessionId / 大象 groupId
  joinedAt: timestamp
  // UNIQUE(conversationId, peerId)
}

Message {
  id: string              // UUID
  conversationId: string   // UUID → Conversation.id
  fromPeerId: string       // UUID → Peer.id
  content: string
  timestamp: timestamp
  type: "text" | "rich_text" | "file" | "image"
}

ConversationState {
  conversationId: string   // UUID → Conversation.id
  execution: "idle" | "executing" | "waiting_confirmation" | "done"
  contextCursor: messageId?
  pendingConfirmation?: {
    messageId: string
    options: string[]
    expiresAt?: timestamp
  }
  updatedAt: timestamp
}
```

存储：SQLite。五张表：peers, conversations, conversation_participants, messages, conversation_states。

**ConversationParticipant 设计说明：**
- 统一管理参与者和插件会话绑定，替代原来的 `Conversation.participants` + `Conversation.bindings` + `ai_sessions`
- 发消息到飞书：查 `conversation_participants` 找 `pluginName=feishu` 的行 → `sessionId` 就是飞书 groupId
- 调用 CC：查 `conversation_participants` 找 `pluginName=claude-code` 的行 → `sessionId` 就是 CC sessionId
- CLI --resume：同上拿 CC sessionId → `claude --resume <sessionId>`
- 一个对话可以有多个同插件参与者（如飞书群里有两个人类 peer）

## Feasibility Notes

- **飞书 Bot 主动发消息**：飞书 Bot 可以在群聊中主动发消息（无时间限制），可以给 24 小时内互动过的用户发单聊消息。Omni 的使用场景是 Bot 在群聊中发消息，不受 24 小时限制。
- **飞书确认卡片**：飞书支持 Interactive Card（消息卡片），可以包含按钮。用户点击按钮后 Bot 收到回调。可用于实现 confirmation 流程。
- **进程管理**：Omni Core 通过 `launchd` plist 在 Mac Mini 上常驻，崩溃自动重启。
- **数据存储**：SQLite。支持并发读写，消息持久化可靠。
- **消息幂等**：每条消息有唯一 ID，插件去重。
- **SDK session 与 CLI 互通**：SDK `query()` 创建的 session（`persistSession: true`）会写入 `~/.claude/projects/`，CLI 通过 `claude --resume <sessionId>` 可以无缝接手。已验证可行。

## Architecture Decision Record: Why Not Matrix

评估过 Matrix/Tuwunel 作为消息核心，最终否决。原因：

1. **Matrix 不管对话状态。** Omni 需要管理执行状态、确认流程、上下文游标。Matrix 只管消息传输。
2. **需要额外的状态管理层。** 如果用 Matrix，还需要一个 State Service 管理状态，Bridge 要同时和 Matrix + State Service 通信，复杂度更高。
3. **状态和消息不独立。** State Service 需要知道消息（管游标、判断确认请求），本质上已经是一个消息系统。
4. **单用户场景不需要 Matrix 的优势。** Matrix 的联邦、多服务器、多客户端优势在个人工具场景不适用。
5. **自建更简单。** 消息存储用 SQLite 就 50 行代码，状态管理本来就要写，不如合成一个 Omni Core。

## Architecture Decision Record: Why Agent SDK instead of claude -p

评估过 `claude -p`（CLI pipe mode）和 `@anthropic-ai/claude-agent-sdk` 作为 CC 插件实现方式，最终选择 SDK。原因：

1. **SDK 内置 session 持久化。** `claude -p` 无状态，需要 Omni 自己拼上下文（最近 N 条消息、token 裁剪）。SDK 的 `resume` 参数自动加载完整历史，省掉整个上下文管理层。
2. **SDK 与 CLI 互通。** SDK 创建的 session 写入 `~/.claude/projects/`，CLI 可以 `--resume` 接手。`claude -p` 也能做到（通过 `--session-id`），但 SDK 是进程内调用，更干净。
3. **SDK 内置 Hook 事件。** `claude -p` 需要 Omni 改 `~/.claude/settings.json` 安装 hook。SDK 的 `hooks` 参数直接在代码中接收所有事件，不污染全局配置。
4. **SDK 内置权限回调。** `canUseTool` 回调可以直接接飞书确认卡片，不需要外部 hook 的 `PermissionRequest` 绕路。
5. **SDK 内置中断。** `query.close()` + `abortController`，不需要 spawn 子进程、SIGINT/SIGTERM/SIGKILL 递进。
6. **SDK 是官方 API。** `claude -p` 是 CLI 的一个 flag，语义上不是给程序调用的。SDK 的 TypeScript 类型定义完整，有 `AsyncGenerator` 流式输出，开发体验更好。
7. **im2cc 已验证此模式。** im2cc 的 `claude-driver.ts` 就是用 `claude -p --stream-json --resume` 做的，SDK 本质上是这个模式的官方封装。
